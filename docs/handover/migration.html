Configurazione di produzione da verificare

  • APP_ENV=production; Clerk pk_live_/sk_live_; PQ_AUTOMATION_SECRET assente.
  • CLERK_AUTHORIZED_PARTIES e CORS_ORIGIN: origini HTTPS esplicite, coerenti con il dominio pubblico.
  • POSTGRES_PASSWORD casuale; stessa password in DATABASE_URL_DOCKER, host postgres. Non cambiare solo .env su un DB già inizializzato.
  • ERP_SYNC_TOKEN obbligatorio, concordato; S3_KEY_PREFIX=erp e BACKUP_REMOTE_PREFIX=backups/postgres per conservare le chiavi correnti. Un cambio prefisso richiede anche migrazione dei riferimenti.

03 / PREPARAZIONE DESTINAZIONE

Preparare senza spostare il traffico

Dimensionamento iniziale suggerito: 4 vCPU, 8 GB RAM, 80–100 GB SSD per la sola produzione, con margine per Chromium e build. Non è un benchmark o una garanzia di capacità; rivalutare con concorrenza reale, allegati e retention. Staging aggiuntivo richiede ulteriore margine.

  1. Installare un sistema operativo supportato, Docker Engine e Compose v2, Git, Node 22 per il preflight. Aggiornamenti OS, SSH a chiave e firewall verificati. PostgreSQL/API non devono essere esposti a Internet.
  2. Preparare /srv/soul-pq e /srv/pq-migration con proprietario tecnico corretto; la seconda cartella deve avere permessi 0700. I dump sono dati riservati.
  3. Clonare il repository con autenticazione del cliente e fissare il commit della release approvata. Il codice correttivo 1.2.1 è nel commit 66130dc; usare il commit di consegna successivo se include solo documentazione.
git clone --branch main --single-branch \
  https://github.com/Chromery/soul-PQ-03S.git /srv/soul-pq
cd /srv/soul-pq
git log -1 --oneline
git status --short
# Verificare il commit approvato prima della build.
chmod 600 .env
node scripts/deployment-preflight.mjs .env
docker compose -p soul-prospect-qualifier build api web postgres-backup

Il file .env deve essere già stato trasferito/configurato in modo protetto. Copiare prima anche 00_prezzari2026/, altrimenti il preflight fallisce correttamente. Non copiare node_modules, cache npm, build locali, file di test o credenziali dell'automazione.

Trasferimenti preliminari

Copiare fonti e, se necessario, oggetti S3 mentre la sorgente è operativa; verificarli con checksum. Fare poi una verifica differenziale finale durante il fermo. Usare operazioni di copia, non sync con cancellazione. Se si mantiene lo stesso bucket, verificare che la nuova chiave possa leggere e scrivere solo quanto previsto.

Non avviare ancora l'API con un DB di produzione copiato e credenziali esterne reali: i lavori in background possono produrre scritture. La preparazione è distinta dal cutover. Sulla VPS nuova non serve replicare l'architettura Git worktree del vecchio server.

04 / FINESTRA DI MIGRAZIONE — SORGENTE

Congelare e acquisire il punto finale

Concordare il fermo con Soul e l'ERP; completare o annullare con criterio lavori in corso, notificare indisponibilità e impedire nuovi sync. L'ERP deve conservare/reinviare gli eventi pendenti secondo una procedura concordata.

SORGENTE ATTUALE, non sulla VPS nuova: usare la configurazione effettiva di produzione. Prima di fermare servizi verificare progetto, branch e nomi con i comandi sotto. Il database resta avviato.

cd /home/debian/dev/Dashboard-generale-03S-main
git branch --show-current
docker compose -p soul-prospect-qualifier ps
docker compose -p soul-prospect-qualifier stop web api postgres-backup
umask 077
mkdir -p /home/debian/pq-migration-20261002
docker compose -p soul-prospect-qualifier exec -T postgres \
  pg_dump -U soul -d soul_pq -Fc \
  > /home/debian/pq-migration-20261002/production-final.dump
docker compose -p soul-prospect-qualifier exec -T postgres \
  pg_restore -l \
  < /home/debian/pq-migration-20261002/production-final.dump

Se dump o verifica falliscono, fermarsi. Non usare un file parziale. Per l'esecuzione automatizzata aggiungere gestione esplicita degli exit code, non concatenare comandi ignorando gli errori.

Archiviare i due volumi non SQL

docker run --rm --network none \
  --mount type=volume,source=soul-prospect-qualifier_erp_audit_logs,target=/data,readonly \
  --entrypoint tar postgres:17-alpine -C /data -czf - . \
  > /home/debian/pq-migration-20261002/erp-audit.tgz
docker run --rm --network none \
  --mount type=volume,source=soul-prospect-qualifier_imu_delibere_cache,target=/data,readonly \
  --entrypoint tar postgres:17-alpine -C /data -czf - . \
  > /home/debian/pq-migration-20261002/imu-delibere.tgz
cd /home/debian/pq-migration-20261002
sha256sum production-final.dump erp-audit.tgz imu-delibere.tgz > SHA256SUMS

Prima verificare i nomi con docker volume inspect: un nome errato potrebbe creare un volume vuoto. Cartella e data sono un esempio: usare un percorso nuovo per la finestra effettiva e non sovrascrivere backup precedenti.

05 / TRASFERIMENTO E RIPRISTINO — DESTINAZIONE

Ripristinare su un DB nuovo e vuoto

Trasferire via SSH/SFTP gli artefatti finali in /srv/pq-migration/ sulla VPS cliente; mantenere accesso 0700 e file 0600. Copiare le fonti prezzari nel clone e verificare checksum e oggetti remoti. Il vecchio ambiente resta fermo alle scritture.

cd /srv/pq-migration
sha256sum -c SHA256SUMS
cd /srv/soul-pq
node scripts/deployment-preflight.mjs .env
docker compose -p soul-prospect-qualifier up -d postgres
docker compose -p soul-prospect-qualifier exec -T postgres \
  psql -U soul -d soul_pq -Atc \
  "SELECT count(*) FROM pg_tables WHERE schemaname='public';"
Il conteggio deve essere 0 e il container deve essere sulla VPS NUOVA. Se non è vuoto, fermarsi e capire perché. Non usare --clean o DROP per “far funzionare” la procedura. Non iniziare con seed o migrazioni prima di ripristinare il dump completo.
docker compose -p soul-prospect-qualifier exec -T postgres \
  pg_restore -U soul -d soul_pq --no-owner --no-privileges \
  --single-transaction --exit-on-error \
  < /srv/pq-migration/production-final.dump

Verificare exit code e conteggi rispetto allo snapshot finale, non ai conteggi storici del report. I ruoli del DB sono creati dal nuovo ambiente; la password viene dalla sua configurazione. Il dump custom contiene SQL: trattarlo come input fidato e riservato.

Ripristino audit e documenti IMU

docker volume create soul-prospect-qualifier_erp_audit_logs
docker volume create soul-prospect-qualifier_imu_delibere_cache
docker run --rm -i --network none \
  --mount type=volume,source=soul-prospect-qualifier_erp_audit_logs,target=/data \
  --entrypoint tar postgres:17-alpine -C /data -xzf - \
  < /srv/pq-migration/erp-audit.tgz
# Ripetere con volume ..._imu_delibere_cache e imu-delibere.tgz.

Anche i volumi devono essere nuovi/vuoti. Estrarre solo archivi propri verificati; non estrarre contenuti non fidati sulla root dell'host. [PostgreSQL 17: ripristino e sicurezza]

06 / AVVIO E CAMBIO TRAFFICO

Una sola produzione scrivente

Verificare che la vecchia API sia ferma e che file e DB siano allo stesso punto finale. La nuova immagine applica le migrazioni senza seed. Eseguire prima il comando esplicito per poter controllare l'esito, quindi avviare.

cd /srv/soul-pq
docker compose -p soul-prospect-qualifier run --rm --no-deps api \
  npm run db:migrate:deploy --workspace @soul/api
docker compose -p soul-prospect-qualifier up -d api web
docker compose -p soul-prospect-qualifier ps
curl --fail http://127.0.0.1:8080/api/health
curl -I http://127.0.0.1:8080/

Conservare output delle migrazioni e health check senza dump delle variabili d'ambiente. Verificare log API per errori di DB/S3/Clerk, non solo la pagina iniziale. Il prezzario può completare abbinamenti mancanti in background; non esegue stime automatiche.

Cloudflare / proxy HTTPS

  • Il tecnico responsabile della zona instrada il dominio pubblico verso il nuovo tunnel/origin su 127.0.0.1:8080; DB e API restano privati.
  • Non avviare contemporaneamente due connettori dello stesso tunnel diretti a database diversi. Cloudflare può distribuire il traffico tra connettori: non è un meccanismo di migrazione sequenziale.
  • Preparare una rotta/tunnel dedicato e commutare in modo controllato; verificare che il vecchio connettore non possa ricevere traffico scrivente. Non fermare un servizio condiviso con altri siti senza verificarne le route.
  • Se si cambia hostname: configurare Clerk, DNS/TLS, origini autorizzate, ERP ed estensione prima del collaudo. Non disabilitare l'autenticazione per aggirare un problema di dominio.

Avviare il backup e verificarlo

docker compose -p soul-prospect-qualifier up -d postgres-backup
docker compose -p soul-prospect-qualifier run --rm --no-deps \
  -e BACKUP_ONCE=true postgres-backup

Richiedere exit code 0, dump leggibile e oggetto effettivamente presente nel namespace remoto di produzione. Verificare orario 03:00 Europe/Rome e retention locale 14 giorni; quella remota dipende dalla policy del provider.

07 / COLLAUDO E ROLLBACK

Accettare o tornare indietro, senza perdere dati

VerificaEsito atteso
Release / loginVersione concordata, Clerk live; accesso reale di admin e operatore, ruoli/nome corretti. Nessuna identità di automazione in produzione.
Dati e documentiConteggi coerenti con dump finale; aprire studio, planimetria, allegati e fonti prezzari. Verificare alcuni checksum documentali, non solo i nomi file.
Flussi applicativiCon Soul, su un elemento di collaudo concordato: nota/salvataggio, editor, IMU, gruppo e PDF V3, bozza/storico. Verificare su Chrome Windows del cliente e Safari.
ERPCon integratore: sync controllato, ID, appuntamento, note, esito con data/ora e presentazione già creata. Richiesta senza token: 401; nessun evento perso nel fermo.
Servizi e backupNeuralWatt, documenti S3 e render PDF funzionanti; backup remoto fresco e prova di restore in ambiente isolato.
ConsegnaOra UTC del cutover, owner, commit, checksum del dump, checklist firmata ed eventuali anomalie. Riaprire sync/operatività solo dopo accettazione.

Rollback prima di nuove scritture utente

Fermare la nuova API e il nuovo worker backup; ripristinare la rotta all'origin vecchia e riavviare i servizi precedenti. Verificare che il nuovo ambiente non resti raggiungibile. Considerare anche eventuali scritture dei job in background: valutare se debbano essere riportate indietro.

Rollback dopo nuove scritture

Non riaccendere semplicemente il vecchio DB. Fermare i due ingressi, acquisire un dump finale della destinazione e concordare ripristino inverso o correzione in avanti. Conciliare eventi ERP e allegati nuovi. Reindirizzare il traffico a una copia vecchia senza recuperare le modifiche comporta perdita di dati.

Mai: docker compose down -v; seed demo in produzione; copia a caldo della directory PG; restore sopra un database in uso; cancellazione del server vecchio prima del termine di rollback; due API attive su DB divergenti.

Conservare vecchia VPS e backup protetti per una finestra concordata, ad esempio 7–14 giorni, poi rimuovere i dati con autorizzazione del titolare. Non è una prescrizione normativa: retention e cancellazione vanno definite dal cliente.

08 / ESERCIZIO E CHECKLIST FINALE

Dopo la migrazione

  • Monitoraggio: disponibilità HTTPS/health, crescita spazio e log, RAM/swap, code di lavoro, errori ERP/NeuralWatt, certificati e stato connettore.
  • Allarmi iniziali: backup non riuscito o assente da oltre 24–26 ore, disco oltre 80%, riavvii ripetuti, aumento anomalo 401/403/5xx. Soglie da adattare, destinatari reali e prova di ricezione obbligatoria.
  • Restore periodico: dump e campione allegati in ambiente isolato, senza token ERP/live o invio a sistemi esterni. Registrare tempi di recupero osservati; definire RPO/RTO aziendali.
  • Aggiornamenti: pianificare PDF.js e runtime, audit OS/container, isolamento Chromium e dipendenze residue del report. Non usare npm audit fix --force alla cieca.
  • Accessi: rimuovere tecnici non più incaricati, ruotare credenziali condivise dopo il collaudo coordinato, attivare MFA e recupero account; custodia vault sotto controllo cliente.
  • Backup: cifratura/permessi, versioning e lifecycle del provider verificati. Il DB non contiene allegati né Clerk: prevedere protezione anche di questi componenti.
