01 / PERIMETRO E RECUPERABILITÀ

Cosa è stato controllato

  • Codice di autenticazione, autorizzazioni, ERP, storage, PDF, backup, bootstrap e configurazione Docker/Nginx.
  • Separazione effettiva di ambienti, credenziali e prefissi; porte, spazio disco, log e fonti locali dei prezzari.
  • Dipendenze npm, ricerca mirata di segreti nei file versionati e presenza storica di file .env. Nessun segreto Clerk/chiave privata trovato dai pattern esaminati; non è una scansione esaustiva della cronologia.
  • Browser Chromium su staging con identità tecnica dedicata; dati simulati nei test distruttivi e campione reale solo in lettura.
  • Produzione: configurazione, dump in lettura, deploy correttivo e smoke test. Nessun import ERP valido di prova, attacco di saturazione o test distruttivo sui dati del cliente.

Dump PostgreSQL in formato custom, ripristinato con --single-transaction --exit-on-error --no-owner --no-privileges in un PostgreSQL 17 temporaneo senza rete. Il container di prova è stato eliminato al termine; il database originale è rimasto operativo.

02 / FINDINGS DI SICUREZZA CORRETTI

Accessi, dati e avvio

S01 · Alta — OTP pubblico dell'account di automazione

Gli indirizzi di test Clerk usano un OTP pubblico per design [Clerk]. Un grant applicativo rendeva tale identità utilizzabile nello staging pubblico.

Corretto: ulteriore segreto casuale lato server richiesto a ogni richiesta, anche con identità in cache. Cookie HttpOnly, Secure, SameSite Strict, limitato a /api; niente invio a Clerk o S3. Le identità di test restano vietate in produzione.

Verifica: rimuovendo il solo segreto da una sessione Clerk valida, l'API passa da 200 a 403.

S02 · Alta — Chiavi storage e isolamento documentale

Segmenti .. e chiavi esterne al namespace documenti potevano raggiungere lo storage. Sette documenti legacy dello staging puntavano ancora al prefisso di produzione.

Corretto: validazione di segmenti/prefissi, rifiuto namespace backup, confine staging/erp per lettura PDF e cancellazione. Sette file copiati in staging, checksum verificati, riferimenti DB aggiornati in transazione. Nessun originale cancellato.

Limite: le credenziali del provider restano condivise; il controllo applicativo non sostituisce policy S3 indipendenti.

S03 · Alta — Password interna DB dimostrativa

Entrambi gli ambienti usavano ancora la password iniziale. Non risultavano porte PostgreSQL pubblicate su tutte le interfacce.

Corretto: password casuali distinte, ruolo PostgreSQL e configurazione API/backup riallineati. Nessun valore riportato nei documenti. File .env con permessi 0600.

S04 · Alta — Seed demo nel comando Docker standard

Un deploy senza l'override temporaneo eseguiva il seed, potenzialmente alterando dati e generando confusione in una migrazione.

Corretto: avvio standard senza seed, blocco esplicito del seed in produzione, preflight di configurazione e README aggiornato.

Non attribuiamo a questo rischio gli episodi storici di stime inattese: manca una prova causale su quelle importazioni.

03 / FINDINGS OPERATIVI CORRETTI

Backup e protezioni HTTP

ID / prioritàEvidenza e correzione
S05 · AltaBackup di ambienti diversi nello stesso namespace. Stesso bucket, prefisso e formato nome, con esecuzione giornaliera coincidente: rischio di sovrascrittura. Staging ora usa staging/backups/postgres; backup reale completato e caricato sul nuovo prefisso. Non si assume che tutti i backup remoti storici siano validi per produzione: verificarli prima del restore.
S06 · MediaFalso successo / file parziale di backup. Il fallimento di pg_dump non restituiva sempre un errore utile. Ora file temporaneo .part, verifica dell'indice, rename dopo successo, permessi 0600 e errore propagato per dump/upload. Il dump locale valido resta recuperabile se il cloud non risponde. Test con errori simulati e prova reale.
S07 · MediaUpload non PDF e decoding permissivo. Ora base64 canonico, MIME data URI, firma, fine file e parsing PDF; limite 40 MiB e 1–500 pagine. Rifiuto prima di scrivere su S3. Non è un antivirus né una garanzia contro ogni PDF ostile.
S08 · MediaAutenticazione dopo il parsing di body grandi. Le scritture utente/ERP sono ora autorizzate prima del parser JSON; restano i controlli di ruolo sul controller. Test: JSON invalido anonimo restituisce 401, non raggiunge il parser.
S09 · MediaHeader e cache incompleti. Aggiunti nosniff, SAMEORIGIN, policy referrer, CSP di base e no-store sulle risposte API predefinite. Rimossa esposizione X-Powered-By. CSP non ancora restrittiva per gli script; i download esplicitamente cacheabili mantengono la propria policy.
S10 · MediaDefault e consumo del disco. Porte Compose di default su loopback; log Docker limitati a 3×10 MB per container ricreato, init e no-new-privileges per API. Esclusi backup/segreti/evidenze dal contesto di build. Eliminate cache obsolete e 20 immagini API senza tag/non in uso; conservate immagini attive e rollback. Le immagini eliminate sono ricostruibili da Git.
Nessuna rotazione del token ERP di produzione, nessun cambio DNS, trasferimento di account o cancellazione di allegati è stato eseguito. Questi interventi richiedono coordinamento esterno.

04 / FEATURE REVIEW

Piccoli bug e regressioni

Correzioni funzionali incluse

  • Upload oltre 1 MB: Nginx applicava il limite predefinito fuori dalla route ERP. Ora il proxy accetta 64 MiB, con autenticazione anticipata e validazione PDF applicativa. Una richiesta autenticata da 2 MiB raggiunge il controllo immobile senza creare dati.
  • Riavvio lento: l'abbinamento prezzari rileggeva e riscriveva tutti gli immobili prima dell'health check. Ora completa in background solo gli abbinamenti mancanti e riusa l'elenco prezzari. Import e aggiornamenti mirati conservano il proprio ricalcolo.
  • Ambiente nello stato sistema: era letto NODE_ENV, uguale a production anche in staging. Ora viene usato APP_ENV.
  • Asset JavaScript mancanti: ricevevano HTML della SPA con risposta 200. Ora restituiscono 404; gli asset con hash sono cacheabili, index.html resta non cacheabile.

06 / GATE DI CONSEGNA

Accettazione consigliata

  1. Confermare il perimetro: solo produzione sulla VPS cliente o anche staging; mantenimento del dominio attuale o dominio aziendale.
  2. Assegnare gli account: proprietario e fatturazione di GitHub, Clerk, Cloudflare/DNS, B2 e NeuralWatt. Registrare almeno due referenti tecnici e il piano di recupero accessi.
  3. Separare i segreti: token ERP e chiavi storage distinti; passaggio tramite vault/canale protetto. Il tecnico verifica che una chiave staging non legga oggetti di produzione.
  4. Concordare i rischi residui: priorità e tempi di migrazione PDF.js/runtime, audit nominativo, monitoraggio e collaudo professionale del catalogo.
  5. Pianificare il fermo: nessuna doppia produzione scrivente. Dump finale, checksum, restore su nuovo DB, smoke test e cambio traffico con rollback documentato.
  6. Collaudo Soul: login di un admin e un operatore, studio reale, PDF/planimetria, salvataggio e presentazione; sync con l'integratore. Conservare il verbale e l'ora di cutover.

Verifica finale produzione: 1.2.1 online, Clerk live, health DB positivo, API protette; backup prima e dopo la rotazione della password caricati correttamente. Preflight della configurazione di produzione superato.
